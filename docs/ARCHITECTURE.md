# WATHB — المعمارية المقترحة

> **المعيار المعتمد (إصدار موحّد 1.0، 2026-10-28):** هذه الوثيقة هي العقد المعماري للمنتج. نطاق المنتج النهائي شامل ما في `PRODUCT_REQUIREMENTS.md`؛ ترتيب التنفيذ لا يحذف وظائفه.

## الحدود والطبقات

Flutter للعميل؛ Supabase Auth/PostgreSQL/Storage/Realtime خدمات مرشحة وليست متصلة حاليًا. طبقات `presentation → application → domain ← data adapters`؛ المجال مستقل عن Flutter وSupabase. وحدات: auth, profile, friendships, activities, comments, teams, career/results, player_reviews, venues, notifications, settings/moderation. اختيار مكتبة حالة وDI واحدة بعد تحقق إصدار Flutter؛ تسجل الإصدارات المثبتة ولا تكرر أدوات الحالة.

المنصات المستهدفة بحد أدنى Android API 26 وiOS 15. اختيار مكتبات Flutter وإعداد البناء مشروط بالتحقق الفعلي من دعمها لهذين الحدين؛ بناء واختبار iOS يتطلب macOS/Xcode.

العرض يدير RTL والثيم واللغة والحالات؛ التطبيق ينسق حالات الاستخدام؛ المجال يحدد قواعد الحالات والانتقالات؛ المستودعات تحقق العقود؛ قاعدة البيانات/RPC تفرض الصلاحيات والتزامن. لا يفرض العميل قواعد أمنية حساسة. يستعمل التخزين الآمن للجلسة، وروابط عميقة تتحقق من المستلم والحالة.

## الخدمات والبيئات والقرارات

- Supabase project غير مؤكد. يلزم أن ينشئه/يختاره المستخدم، يحدد المنطقة/الخطة، ويضبط البريد/redirects؛ لا نطلب منه سرًا. anon/publishable key فقط بالتطبيق مع RLS، وservice role خادمي فقط.
- Push يحتاج قرار مزود (مثل FCM/APNs عبر Supabase أو خدمة مناسبة)، إعداد حسابات المنصات ومفاتيح خادمية وموافقة الإشعارات. داخل التطبيق يعمل مستقلًا عن push.
- خرائط/ترميز جغرافي يحتاج مزودًا ومفاتيح وقيود ميزانية وخصوصية. حتى اختياره، يمكن إدخال عنوان/رابط موقع يدويًا؛ لا ادعاء بخريطة أو ملاحة متصلة.
- الصور عبر Supabase Storage إذا اعتمد، مع سياسات مسار/حجم/نوع؛ تتطلب سياسة صور عامة/خاصة واحتفاظ.
- الدفع والحجز لا ينفذان قبل اختيار مزود ونموذج تشغيلي وقانوني.
- بيئات dev/test/prod منفصلة، migrations المصدر الوحيد للمخطط، وإعدادات منفصلة؛ لا secrets في git أو العميل.

## قواعد التزامن والتدفق

كل تعديل حساس عبر RPC ذرية أو معاملة: انضمام/استجابة للمقعد، إنشاء مع مالك ودعوات، إلغاء/تعديل وإشعار، توليد/حفظ فرق، تأكيد حضور/نتيجة، تسجيل تقييم، حذف الحساب. تستخدم قيود فريدة ومفاتيح idempotency وقفلًا مناسبًا للسعة. نتائج RPC رموز نطاق واضحة؛ لا يكتب العميل عدادًا مشتقًا. Realtime تحسين تحديث وليس مصدر سلامة.

التمييز الإلزامي: الدعوة `invited` طلب موجه؛ قبولها `accepted` حجز مقعد؛ رفض/انسحاب يحرر المقعد حسب السياسة. الحضور `attended/no_show` حقيقة لاحقة يؤكدها المنظم/آلية مراجعة ولا يستنتج من القبول. لا يدخل السجل الرياضي أو أهلية التقييم إلا حضور مثبت. نتيجة المباراة مستقلة عن الحضور وتتأكد وفق صلاحيات ونافذة اعتراض.

## عقود متعددة الرياضات والفرق

رياضة ومراكز ذات قاموس/ترجمة، وقواعد خاصة بالرياضة إن لزم في بيانات منظمة versioned لا أعمدة تفترض كرة القدم. توزيع الفرق يقبل استراتيجية `random`, `manual`, `positions`؛ يثبت seed/نسخة خوارزمية عند العشوائي للتدقيق. وضع المراكز يوازن التغطية فقط إذا كانت بيانات المراكز موثوقة؛ يبين النقص ولا يستنتج مستوى اللاعب. تعديلات المنظم اليدوية تحفظ كقيود عند إعادة التوزيع إن اختار الاحتفاظ بها. كل حفظ يعيد التحقق من المجموعة المؤهلة: كل لاعب مرة واحدة بالضبط، لا لاعب غير مؤهل، ولا فريق فوق حد محدد إن عرّف. المعاملة تكتب التشكيل كاملًا أو لا تكتب شيئًا.

## جودة وتشغيل

أخطاء منقحة، لا PII/رموز في السجلات، مراقبة من دون أسرار؛ migrations مراجعة، نسخ احتياطية واستعادة مجربة، وإجراء حذف/تصدير. CI لاحقًا يحلل ويختبر ويفحص الأسرار والسياسات. دعم iOS يتطلب macOS/Xcode واختبارًا فعليًا؛ لا يكفي بناء Android.
